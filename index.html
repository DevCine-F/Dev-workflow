I. QUY ĐỊNH CHUNG & GIAO TIẾP

  • Họp hằng ngày (Daily Meeting): Thời gian và hình thức họp sẽ được thực hiện linh hoạt theo thông báo cụ thể trên nhóm trao đổi chính.
  • Kỷ luật thời gian: Mọi thành viên cần cập nhật tiến độ công việc trước buổi họp để đảm bảo nội dung trao đổi tập trung vào các vấn đề cần giải quyết.

II. QUY TRÌNH LÀM VIỆC

Áp dụng tinh thần từ quy trình doanh nghiệp, dự án sẽ đi qua các checkpoint quan trọng:

01
Giai đoạn Khảo sát Planning

Chốt danh sách tính năng (Usecase) và thiết kế giao diện (UI/UX). Đây là nền tảng để định hình sản phẩm.

02
Giai đoạn Kỹ thuật Architecture

Thiết kế Cơ sở dữ liệu và API trước khi bắt đầu viết code để đảm bảo tính nhất quán và hiệu suất hệ thống.

03
Giai đoạn Phát triển Development

Thực hiện lập trình các chức năng dựa trên thiết kế và tài liệu kỹ thuật đã được phê duyệt.

04
Kiểm soát chất lượng QC / Review

Mỗi tính năng sau khi hoàn thành phải được nhóm trưởng hoặc thành viên khác kiểm tra (Review) mã nguồn trước khi xác nhận.

III. QUY ĐỊNH GITHUB (PUSH/PULL CODE)

1. Các lệnh Git cơ bản (Copy & Run)

Mọi thành viên cần tuân thủ trình tự lệnh để tránh xung đột mã nguồn:

Cập nhật code mới nhất trước khi làm: 

git pull origin main

Kiểm tra các file đã thay đổi: 

git status

Thêm tất cả thay đổi vào hàng chờ: 

git add .

Xác nhận thay đổi (Theo quy tắc Commit bên dưới): 

git commit -m "feat(customer): add movie list view"

Đẩy code lên nhánh chính: 

git push origin main

2. Quy tắc đẩy code (Commit Strategy)

A. Cấu trúc chuẩn

Mỗi Commit Message phải bao gồm:

<type>(<scope>): <description>
  • Type: Loại thay đổi (Bắt buộc).
  • Scope: Phạm vi/Module thay đổi (Tùy chọn nhưng khuyến khích).
  • Description: Mô tả ngắn gọn bằng Tiếng Anh (Bắt buộc).

B. Các Type bắt buộc (Mandatory Types)

Type Ý nghĩa (Dành cho việc chọn loại)
feat Thêm một tính năng mới (Feature)
fix Sửa một lỗi (Bug fix)
docs Thay đổi liên quan đến tài liệu, comment
style Thay đổi về format code (khoảng trắng, dấu phẩy...) - KHÔNG đổi logic
refactor Tái cấu trúc mã nguồn - KHÔNG sửa lỗi, KHÔNG thêm tính năng
perf Cải thiện hiệu suất code (Performance)
test Thêm hoặc sửa các file unit test
chore Cập nhật thư viện, cấu hình build, công cụ hỗ trợ (như .gitignore)

C. Hướng dẫn chi tiết & Yêu cầu

  • Ngôn ngữ (Language): Bắt buộc sử dụng Tiếng Anh cho toàn bộ nội dung commit message. (Ghi chú nội bộ vẫn có thể dùng Tiếng Việt).
  • Phạm vi (Scope): Sử dụng các scope tương ứng với cấu trúc DevCine: customer, admin, ui, auth, db.
  • Mô tả (Description): Sử dụng câu mệnh lệnh (Imperative mood), thì hiện tại (ví dụ: dùng add thay vì added). Không viết hoa chữ cái đầu tiên, không dùng dấu chấm cuối câu.

D. Ví dụ minh họa (Examples)

Nội dung thay đổi Commit Message chuẩn
Thêm trang danh sách phim feat(customer): add movie list view
Sửa lỗi không hiển thị suất chiếu fix(admin): resolve showtime display issue
Cập nhật file README dự án docs: update project installation guide
Tối ưu lại hàm tính tiền vé refactor: optimize ticket price calculation
Thêm thư viện Axios để gọi API chore: install axios library
Sửa format code trong Sidebar style(admin): format sidebar component code

IV. QUY TẮC ĐẶT TÊN (NAMING CONVENTION)

Sử dụng Tiếng Anh và tuân thủ các quy tắc sau:

1. Đối với Thư mục (Folder) và Tệp tin (File)

  • Quy tắc: Sử dụng PascalCase (Viết hoa chữ cái đầu của mỗi từ).
  • Ví dụ: ComingSoon, UserManagement, ProductDetail.vue, HomeView.vue.

2. Đối với Biến (Variable) và Hàm (Function)

  • Quy tắc: Sử dụng camelCase (Viết thường chữ đầu, viết hoa các chữ sau).
  • Ví dụ: getNameAccount, isUserLoggedIn, totalPrice, calculateTotal().

3. Các nguyên tắc bổ trợ (Từ tiêu chuẩn Vietnix)

  • Nguyên tắc S-I-D: Tên phải Ngắn gọn (Short), Dễ hiểu (Intuitive), và Mô tả đúng ý nghĩa (Descriptive).
  • Tránh viết tắt: Luôn ưu tiên viết đầy đủ để tránh gây hiểu lầm cho thành viên khác (VD: dùng event thay vì ev).
  • Tránh lặp từ: Không lặp lại tên Class/Module trong tên hàm (VD: trong class User, dùng updateProfile() thay vì updateUserProfile()).
  • Số ít/Số nhiều: Đối với mảng (Array) hoặc danh sách, bắt buộc dùng danh từ số nhiều.
  • Cấu trúc hàm (A/HC/LC): Tên hàm nên theo thứ tự: Hành động + Ngữ cảnh cao + Ngữ cảnh thấp.

Ví dụ: getUserMessages, shouldDisplayLoading.

V. QUY ĐỊNH BẢO MẬT & ĐIỀU CẤM KỴ

Để đảm bảo tính riêng tư và bản quyền của đồ án, mọi thành viên DevCine phải tuân thủ tuyệt đối:

Bảo mật thông tin nội bộ

Mọi thông tin về dự án, tiến độ và kỹ thuật chỉ được thảo luận trong phạm vi nội bộ nhóm. Tuyệt đối không chia sẻ ra bên ngoài.

Quản lý tài liệu (URD/ERD)

Các file đặc tả, sơ đồ kiến trúc và file thiết kế không được gửi cho bất kỳ cá nhân nào ngoài danh sách thành viên DevCine.

Đường dẫn nội bộ & Demo

Các liên kết demo, link truy cập hệ thống tạm thời chỉ cung cấp cho thành viên dự án và Giảng viên hướng dẫn.

Cấu trúc lõi hệ thống

Nghiêm cấm việc xóa hoặc đổi tên các thư mục gốc khi chưa có sự đồng ý của cả nhóm để tránh xung đột mã nguồn.

Hình thức kỷ luật

Vi phạm bất kỳ điều nào trong các quy định bảo mật và điều cấm kỵ nêu trên sẽ dẫn đến:

  • Huỷ bỏ toàn bộ kết quả đánh giá đối với thành viên vi phạm.
  • Trục xuất (kick) ngay lập tức khỏi nhóm dự án.

VI. CẤU TRÚC THƯ MỤC NGUỒN (SRC/)

src/
├── api/                    # Quản lý toàn bộ lời gọi API (Axios instance)
│   ├── admin/              # API cho các chức năng quản trị (phim, rạp, nhân sự)
│   └── customer/           # API cho khách hàng (đặt vé, lịch chiếu, profile)
├── assets/                 # Tài nguyên tĩnh dùng chung cho toàn dự án
│   ├── images/             # Logo, banners, placeholder ảnh phim
│   ├── icons/              # Các file svg, icon tùy chỉnh
│   └── styles/             # Global CSS, Tailwind config, font-face
├── components/             # Các thành phần giao diện tái sử dụng (UI Components)
│   ├── common/             # Dùng ở cả 2 bên (AppButton, AppModal, AppLoading)
│   ├── admin/              # Component chỉ Admin dùng (Sidebar, StatCard, RevenueChart)
│   └── customer/           # Component chỉ Khách dùng (MovieCard, SeatMap, BookingTimer)
├── composables/            # Logic tái sử dụng (useAuth, useSocket, useTheme)
├── layouts/                # Các khung giao diện chính (Layout mẫu)
│   ├── AdminLayout.vue     # Layout có Sidebar/Topbar cho quản trị
│   ├── CustomerLayout.vue  # Layout có Navbar/Footer cho khách hàng
│   └── AuthLayout.vue      # Layout tối giản cho trang Login/Register
├── router/                 # Cấu hình định tuyến và Phân quyền (Check Role)
│   ├── admin.js            # Định nghĩa các routes phía Admin
│   ├── customer.js         # Định nghĩa các routes phía Customer
│   └── index.js            # File tổng hợp và xử lý logic Middleware (chặn quyền)
├── stores/                 # Quản lý trạng thái toàn cục (Pinia)
│   ├── auth.js             # Lưu thông tin User, Token, Role
│   └── booking.js          # Lưu thông tin đặt vé tạm thời (phim, ghế, giá)
├── utils/                  # Các hàm bổ trợ (Helper functions)
│   ├── format.js           # Định dạng tiền tệ (VND), ngày tháng (DD/MM/YYYY)
│   └── constants.js        # Lưu các hằng số (Trạng thái vé, Loại nhân viên, API URL)
├── views/                  # Các trang (Page) hoàn chỉnh
│   ├── admin/              # Thư mục chứa các trang quản trị
│   │   ├── Dashboard.vue   
│   │   ├── CinemaManager.vue
│   │   └── StaffManager.vue
│   └── customer/           # Thư mục chứa các trang khách hàng
│       ├── HomeView.vue    
│       ├── MovieDetail.vue
│       └── BookingView.vue
├── App.vue                 # File gốc (Root Component)
└── main.js                 # Điểm khởi tạo chính (Import Pinia, Router, Tailwind)
